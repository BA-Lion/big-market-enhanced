# `.ai`：Coding Agent 开发约束与项目记忆

`.ai/` 是项目级 Agent harness。它保存能够跨会话复用的项目上下文、分层设计、执行约束、问题记录和验证证据，使规划模型、执行模型和审查模型可以在同一套事实与约束下协作。

`.ai/` 不是业务源码目录，也不是聊天记录归档。它不能替代当前用户指令、仓库中生效的 Agent 指令、代码、测试和正式产品文档。

## 1. 设计目标

- 新会话能够从 `index.md` 和 `project.md` 快速恢复必要上下文。
- 架构约束、任务方案和编码步骤分层保存，避免抽象层级混杂。
- 高能力规划模型可以产出足够精确的 `implementation/` 文件，供低级别执行模型按约束实施。
- 每项重要结论都能追溯来源、状态、适用范围和验证证据。
- 已失效的设计和实施文件不会被误当作当前指令。
- 文档数量与任务风险相称，避免简单任务产生无价值记录。

## 2. 生效边界

### 2.1 自动发现

Agent 不会因为 `.ai/` 存在就必然自动读取它。项目必须通过仓库根目录当前生效的 Agent 指令文件，引导 Agent 先读取：

1. `.ai/index.md`；
2. `.ai/project.md`；
3. 索引中与当前任务相关的记录。

不要在本文件中假定根目录一定使用 `AGENTS.md` 或 `AGENTS.override.md`；以当前运行环境实际加载的指令链为准。

### 2.2 权威层级

不同来源负责不同类型的事实，不能用一个简单顺序覆盖全部冲突：

- 当前用户指令和当前生效的 Agent 指令定义本次工作的授权与行为边界。
- `architecture/` 定义长期设计意图、系统边界和架构不变量。
- `decision/` 定义某次任务采用的方案和取舍。
- `implementation/` 定义该方案的具体执行契约。
- 代码、配置和可重复测试反映系统当前的实际状态。
- `test/result/` 保存某次验证的时间点证据，不自动代表当前状态。

当设计意图与实际实现不一致时，不得静默选择其中一方。应判断是实现缺陷、文档过期还是需求已经变化，并更新相应记录或创建 `problem/` 记录。

### 2.3 约束传递

核心约束链为：

```text
architecture
    ↓ 约束方案边界
decision
    ↓ 确定任务方案
implementation
    ↓ 指导编码执行
test/result
    ↓ 提供验证证据
```

必须满足：

- `implementation` 不得突破其引用的 `decision`。
- `decision` 不得突破生效中的 `architecture`。
- 如任务需要改变架构，必须先提出或更新架构记录，再批准任务方案。
- 只有状态为 `approved` 或 `in_progress` 的 implementation 文件可以作为编码依据。
- `completed`、`superseded` 或 `cancelled` 的 implementation 文件只能用于追溯。

## 3. 目录职责

| 路径 | 职责 | 不应包含 |
| --- | --- | --- |
| `index.md` | 当前有效记录的导航和状态总览 | 大段设计正文 |
| `project.md` | 项目技术栈、命令、边界、约定和权威入口 | 单次任务计划 |
| `architecture/` | 长期架构边界、重大取舍和不变量 | 普通任务步骤 |
| `decision/` | 某次开发的方案粗略总结、备选项和取舍 | 文件级编码指令 |
| `implementation/` | 可交给执行模型的详细编码契约 | 未批准的范围扩张 |
| `doc/` | 模块说明、接口语义、关键常量和代码阅读入口 | 重复的正式产品文档 |
| `attention/` | 经验证、跨任务复用的高风险注意项和教训 | 未验证猜测 |
| `problem/` | 未解决问题、复现条件、影响和下一步 | 已完成任务总结 |
| `task/current/` | 当前任务状态、边界、进度、阻塞和链接 | 完整重复的设计正文 |
| `task/future/` | 明确暂缓且仍有价值的工作项 | 未经筛选的想法列表 |
| `test/experience/` | 可复用的测试、启动和排障经验 | 单次测试结果 |
| `test/result/` | 带时间点、环境和命令的验证结果摘要 | 大段原始日志或敏感数据 |
| `test/script/` | `.ai` 工作流需要的轻量验证辅助脚本 | 应属于产品测试体系的正式测试代码 |
| `templates/` | 各类记录的标准模板 | 项目实际记录 |

## 4. 三层设计文档

### 4.1 Architecture：长期架构约束

Architecture 用于记录跨任务长期有效、普通开发不得自行突破的重大设计决策，包括：

- 系统边界、模块职责和依赖方向；
- 数据所有权、事务边界和一致性原则；
- 安全、隐私、兼容性和性能不变量；
- 重大技术选型及被拒绝方案；
- 架构演进、替代关系和迁移要求。

状态：`proposed | accepted | superseded | deprecated`。

只有 `accepted` 的记录构成当前架构约束。被替代记录必须通过 `superseded_by` 指向新记录，不得直接删除。

### 4.2 Decision：任务级方案

Decision 用于记录某次开发准备采用什么方案，以及为什么这样选择。它位于需求与执行规格之间，应包含：

- 问题和目标；
- 本次范围与非目标；
- 相关架构约束；
- 采用的方案；
- 备选方案和取舍；
- 受影响模块；
- 风险、兼容性和验收标准；
- 需要下沉到 implementation 的事项。

状态：`draft | approved | rejected | superseded | cancelled`。

只有 `approved` 的 decision 可以生成 active implementation。需要改变方案时，应先更新或替代 decision，再修改 implementation。

### 4.3 Implementation：执行级编码契约

Implementation 面向编码执行模型，必须把已批准方案转化成低歧义、可验证的操作说明。至少包含：

- 上游 task、decision 和 architecture 链接；
- 基线版本或生成时所依据的代码状态；
- 允许修改与禁止修改的文件；
- 精确到模块、类、函数、接口或数据结构的改动；
- 执行顺序和步骤间依赖；
- 必须保持的不变量；
- 错误处理、边界条件和兼容要求；
- 需要新增或修改的测试；
- 验证命令和通过标准；
- 必须停止并升级的条件。

状态：`draft | approved | in_progress | blocked | completed | superseded | cancelled`。

执行模型不得把模糊描述自行扩展成新的产品或架构决定。出现以下情况必须停止并上报：

- implementation 与代码现状或上游文档冲突；
- 目标文件、符号或接口不存在且无法无歧义定位；
- 需要修改未授权文件或扩大任务范围；
- 需要新增生产依赖、执行数据迁移或采取不可逆操作；
- 验证失败暴露出方案本身存在问题；
- 无法满足某项架构不变量或验收标准。

## 5. 风险分级工作流

### L0：轻量修改

适用：文案、注释、局部样式、显而易见且低风险的小修复。

- 不强制创建 `.ai` 记录。
- 仍必须检查实际代码并执行与风险相称的验证。

### L1：标准任务

适用：跨文件修改、普通功能、局部重构、需要恢复上下文的缺陷。

- 在 `task/current/` 创建任务记录。
- 方案存在明显取舍时创建 decision。
- 执行步骤简单且由同一高能力模型完成时，implementation 可选。

### L2：复杂或模型交接任务

适用：复杂功能、跨模块修改、需要把编码交给低级别执行模型的任务。

- 必须创建 task、decision 和 implementation。
- implementation 必须经过有授权的用户、维护者或规划模型批准后才能执行。
- 必须产生验证结果摘要。

### L3：高风险或架构变更

适用：架构边界、数据迁移、安全、权限、兼容性破坏或不可逆操作。

- 必须创建或更新 architecture。
- 必须创建 task、decision、implementation 和验证记录。
- 必须获得与风险相称的明确批准。
- 必须提供回滚、迁移或恢复策略。

## 6. 记录生命周期

1. 在 `task/current/` 建立任务范围和验收标准。
2. 根据风险等级创建 decision，并引用相关 architecture。
3. 方案批准后创建 implementation。
4. 执行过程中只更新进度、发现和必要偏差，不静默重写已批准目标。
5. 验证后将摘要写入 `test/result/`。
6. 任务完成时：
   - 将 implementation 标记为 `completed`；
   - 更新 task 最终状态；
   - 更新 `index.md`；
   - 将未解决事项转入 `problem/` 或 `task/future/`；
   - 将稳定知识沉淀到 `doc/`、`attention/` 或 `test/experience/`。
7. 已完成记录可以移动到对应目录的 `archive/` 子目录，但不得继续列入“当前有效”索引。

## 7. 通用文档约定

- 实际记录从 `templates/` 中对应模板创建。
- 文件名使用英文短横线命名；需要追溯时间的记录使用 `YYYY-MM-DD-topic.md`。
- 每份记录必须包含 front matter，不得自由发明状态值。
- 使用仓库相对链接，不记录个人机器绝对路径。
- 明确区分：事实、推断、待确认和已废弃内容。
- 同一事实只保留一个权威位置，其他位置使用链接和简短摘要。
- 引用代码时优先记录稳定符号或模块，并在必要时附相对路径；不要依赖容易漂移的行号作为唯一定位方式。
- 测试结果必须记录命令、环境、结果和时间点；不得只写“测试通过”。
- 不保存 API key、访问令牌、私钥、license key、个人信息、客户原始数据或未脱敏日志。
- 临时聊天笔记在任务结束时必须删除、归档或转化为正式记录。

## 8. 索引维护规则

- `index.md` 只列出当前有效或近期需要关注的内容。
- 新增、批准、阻塞、完成、替代、归档或删除记录时，同步更新索引。
- 模板、已完成 implementation 和纯历史测试结果不进入“当前有效”栏目。
- 每个索引条目至少包含：标题、状态、适用范围和相对链接。
- 如索引与文件 front matter 不一致，以文件为证据并立即修正索引。

## 9. 敏感信息与文件所有权

- `.ai/` 中的说明不授予超出当前用户请求和运行环境权限的操作权。
- implementation 声明的“允许修改文件”只能缩小已有授权，不能扩大授权。
- 不以 `.ai/` 中的旧批准替代当前需要的人类批准。
- 不覆盖不属于当前任务的用户修改。
- 原始测试日志、数据库导出和外部客户材料应留在受控系统中；`.ai/` 只保存脱敏摘要和定位信息。

## 10. 初始化检查

将本目录用于新项目时：

1. 填写 `project.md`，清除所有 `TBD`。
2. 在 `architecture/` 中记录已经明确的关键架构约束。
3. 填写 `index.md` 的项目状态和有效记录。
4. 在仓库根目录生效的 Agent 指令中加入 `.ai` 读取入口。
5. 确认目录名称、命令和技术栈与真实项目一致。
6. 删除不适用于该项目的示例，不要把模板内容当成项目事实。
7. 运行 `python .ai/test/script/validate_harness.py` 检查结构、元数据和相对链接。
